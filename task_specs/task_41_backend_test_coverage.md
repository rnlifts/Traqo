# Task 41 — Expand backend test coverage across every module

## Objective
The backend already has a working pytest foundation (`backend/tests/conftest.py` — in-memory SQLite + hand-written in-memory repository doubles, 4 existing test files) but almost none of the use cases built this session have any coverage. Expand it to cover every module's use cases, following the exact patterns already established in `conftest.py`.

## Context
- Tests live in **`backend/tests/`**, a separate directory tree from `backend/src/` — not co-located (this is the standard Python/pytest convention, and this project already follows it; do not change this structure). Existing layout: `backend/tests/unit/` (use-case-level tests with in-memory repo doubles) and `backend/tests/integration/` (route-level tests). Follow this same split.
- `backend/tests/conftest.py` already provides: an in-memory SQLite `test_db` fixture, and hand-written `InMemoryWorkoutPlanRepository`, `InMemoryWorkoutExerciseRepository`, `InMemoryExerciseRepository` classes implementing the real repository interfaces — this is the established pattern for unit-testing a use case without a real database. **Extend `conftest.py` with equivalent in-memory doubles** for any repository interface that doesn't have one yet (sessions, auth, exercise_library) rather than inventing a different testing style.
- **Known limitation to address**: existing tests run against SQLite, which does not enforce foreign-key/cascade behavior the same way Postgres does. The cascade-delete migration bug from earlier this project (missing `ON DELETE CASCADE` on `workout_sessions`' foreign keys, only caught via manual live testing against real Postgres) is exactly the kind of bug a SQLite-only test suite cannot catch. Add a small number of tests that run against a **real Postgres** instance (the existing local dev Postgres is fine for local runs; Task 42's CI setup will use a Postgres service container) specifically to verify cascade-delete behavior end-to-end (deleting a plan actually removes its days/sessions/sets via the DB, not just via application-level orchestration).

## Requirements
Add unit tests (in-memory repo doubles, following the `conftest.py` pattern) for every use case in these modules that doesn't already have one:

**`auth`**: `RegisterUser` (successful registration, duplicate username raises `UsernameAlreadyTakenError`, password gets hashed not stored raw), `LoginUser` (correct credentials succeed, wrong password/username raises `InvalidCredentialsError`), `UsernameValidator.validate_format` (every rule: length bounds, must-start-with-letter, allowed characters, normalization/lowercasing).

**`sessions`**: `StartWorkout` (creates session, week-based resolution, ownership checks), `QuickStartWorkout` (creates plan+day+session atomically, rollback-on-failure behavior already documented in that file's own docstring), `AddWorkoutSet` / `DeleteWorkoutSet`, `FinishWorkout` (can't finish an already-finished session), `DiscardWorkoutSession` (can't discard an already-finished session — this exact rule was verified live during Task 28 but has no automated test), `GetUnresolvedSession`, `GetWorkoutSessionDetail`, `GetWorkoutHistory`, `GetExerciseProgress`. Also cover the "block starting a new session while one is unresolved" behavior added to `StartWorkout`/`QuickStartWorkout` in Task 28 (`UnresolvedSessionExistsError`).

**`workouts`**: `CreateWorkoutPlan`/`UpdateWorkoutPlan`/`DeleteWorkoutPlan` (ownership checks; **the plan-delete guard removal from Task 28 — deleting a plan with sessions must succeed, not raise `WorkoutPlanHasSessionsError` anymore** — write a test that would have caught the constructor-signature regression found during Task 28's live verification, i.e. actually instantiate and call the use case, don't just check it compiles), `ListWorkoutPlans`, day/week CRUD (`CreateDay`, `DeleteDay` — including its `exists_for_day` guard, which is intentionally still active, unlike the plan-level one), `AddExerciseToDay`/`RemoveExerciseFromDay`, set-targets/vary-by-set replacement logic, `week_resolver`'s week-resolution logic (already partially covered per existing `test_week_resolver.py` — check what's missing).

**`exercises`**: `CreateExercise`, `ListExercises`, `DeleteExercise` (the `ExerciseInUseError` guard — deleting an exercise that's used in a plan must be blocked, deleting an unused one must succeed).

**`exercise_library`**: `SearchExercises`/`score_exercise_match` (this is already a pure, testable function per its own docstring — write direct unit tests for it, including the exact "lat pull down" → "Pulldown"-style substring-matching case, and the short-word-exact-match-only rule that prevents single letters from matching everything — both were real bugs caught during live verification and deserve permanent regression tests), `GetMuscleGroups`.

**Route-level integration tests** (new — extend the existing pattern, not the unit-test pattern): `backend/tests/integration/test_workout_routes.py` already establishes this project's integration-test style — `fastapi.testclient.TestClient` wired to a real SQLite database via `app.dependency_overrides[get_db]` (with `PRAGMA foreign_keys=ON`), schema built via `Base.metadata.create_all(engine)`. This exercises the full stack (route → use case → real repository → real DB session), unlike the unit tests' in-memory fakes. **Add equivalent integration test files for the route modules that don't have one yet**: `backend/src/modules/auth/presentation/routes.py` (register, login, check-username — including the rate-limiter `response` param gotcha from Task 33, which only a real HTTP request through the route can catch, not a use-case-level unit test), `backend/src/modules/sessions/presentation/routes.py` (start/quick-start/finish/discard/unresolved — including the exact route-ordering bug from Task 28, where `/unresolved` was shadowed by `/{session_id}`; a real HTTP `GET` to `/unresolved` is what would have caught that, not calling the use case directly), `backend/src/modules/exercise_library/presentation/routes.py` (search, muscle-groups).

**Postgres-backed migration-correctness test** (new, and distinct from the integration tests above — this is a different layer): the integration tests above build their schema from `Base.metadata.create_all()`, i.e. from the current Python model definitions — they do **not** run the actual Alembic migrations, so they can't catch a case where a migration and its model drift apart (exactly what happened with the missing `ON DELETE CASCADE` in Task 28 — the fix required both a model update and a migration, and only the migration is what actually governs production). Add a small dedicated test that runs real Alembic migrations against a real (test) Postgres database, creates a plan with days/sessions/sets, deletes the plan via the real repository, and asserts via direct DB query that everything cascaded. This is the only layer that validates the deployed schema itself, not just the model.

## Do NOT
- Do not move any test files to be co-located with source files — keep the existing separate `backend/tests/` tree structure.
- Do not replace the in-memory SQLite approach for the bulk of unit tests — it's working well and is fast; only the specific cascade-delete behavior needs real-Postgres coverage.
- Do not test framework/library code (SQLAlchemy itself, FastAPI itself) — focus on this app's own use-case logic.

## Acceptance criteria
- [ ] Every use case listed above has at least one passing test, and at least one test per use case that exercises its main failure/edge case (not just the happy path).
- [ ] The `score_exercise_match` tests include the exact "lat pull down" vs. "Pulldown" case and the short-word false-positive case ("T Bar Row" should not match a query containing "lat") — both real bugs found in earlier live verification, now permanent regression tests.
- [ ] The Postgres-backed cascade test actually fails if someone reverts the `ON DELETE CASCADE` migration (verify this by temporarily reverting it locally and confirming the new test catches it, then restoring the migration).
- [ ] The new auth/sessions/exercise_library integration test files actually hit real routes via `TestClient` (not the use cases directly) — verify by temporarily reintroducing the exact route-ordering bug (`/unresolved` registered after `/{session_id}`) and confirming the sessions integration test catches it, then restoring correct ordering. Same for temporarily removing `response: Response` from a rate-limited auth route and confirming its integration test catches the resulting 500.
- [ ] `DeleteWorkoutPlan`'s test actually instantiates and calls the use case with a plan that has sessions, and asserts it succeeds — not just that the file imports cleanly (this specific class of bug — a stale constructor call site — was caught only by live testing, not by any automated check, during Task 28).
- [ ] All new tests pass with `pytest` run from `backend/`.
- [ ] No test depends on network access or a live server being up (aside from the intentionally-separate Postgres-backed cascade test, which needs a real DB connection but not a running app server).

## Review checklist

- [ ] Tests are organized under `unit/` vs `integration/` consistent with the existing split (use-case-level with fakes vs. route-level with a real test client).
- [ ] No production code in `backend/src/` was modified to "make it testable" without being flagged — if something is hard to test as-is, note it rather than silently changing behavior.
