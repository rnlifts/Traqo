# 3.2 — `get_optional_user_id` can't distinguish "no token" from "invalid token"

**Status:** Confirmed valid, deferred. Not started. Do NOT apply the reviewer's
literal suggested fix without reading the "why this is riskier than it looks" section
below — it would reintroduce a bug this codebase already fixed once.

## The finding

`backend/src/infrastructure/security/oauth2.py`:

```python
async def get_optional_user_id(
    credentials: HTTPAuthorizationCredentials | None = Depends(optional_security),
) -> int | None:
    if not credentials or not credentials.credentials:
        return None  # no token provided

    user_id = decode_access_token(credentials.credentials)
    return user_id  # None if token is invalid/expired — same as "no token"
```

`decode_access_token` (`jwt_service.py`) catches `JWTError`/`ValueError` and returns
`None` uniformly for any decode failure (expired, tampered, malformed). There's no
way for a caller of `get_optional_user_id` to tell "this visitor never had a token"
apart from "this visitor had a token but it's expired/invalid."

Confirmed via grep: `get_optional_user_id` is used in exactly one place —
`backend/src/modules/sharing/presentation/routes.py` — on the public/anonymous-allowed
share-link endpoints (`GET /{token}`, `POST /{token}/start`, `POST
/{token}/sessions/{id}/sets`, `POST /{token}/sessions/{id}/finish`).

## Why the reviewer's literal suggested fix is dangerous here

The suggested fix: make `decode_access_token` raise on invalid tokens, and have
`get_optional_user_id` turn that into an `HTTPException(401)`.

This directly conflicts with an already-deliberate design decision in this exact
code. `resolve_and_access_shared_plan`'s own docstring says:

> "Note: 403 is never returned as 401 to avoid triggering frontend
> session-clear redirects. See Phase 3 spec for details."

And `frontend/src/api/client.ts` confirms exactly why:

```ts
client.interceptors.response.use(
  (response) => response,
  (error) => {
    if (error.response?.status === 401) {
      localStorage.removeItem('auth_token');
      localStorage.removeItem('current_user');
      delete client.defaults.headers.common['Authorization'];
      window.location.href = '/login';
    }
    return Promise.reject(error);
  }
);
```

**Any** 401, from **any** request, force-clears the session and hard-redirects to
`/login`. If `get_optional_user_id` starts raising 401 for invalid tokens, then
anyone visiting a public share link with a stale/expired token sitting in their
browser (left over from an unrelated past login, or just an old session that expired
naturally) would get **kicked out to the login page from a link that's supposed to
work without logging in at all**. That's a regression, not a fix — it breaks the
"anyone" share mode's entire point for a chunk of real visitors.

## What a correct fix needs to do instead

Distinguish "invalid token" from "no token" **without ever surfacing it as a hard
401** on these routes. Some options, not yet evaluated in depth:

1. `get_optional_user_id` returns a richer result than `int | None` — e.g. a small
   result object/tuple like `(user_id: int | None, token_was_invalid: bool)` — and
   each sharing route decides what to do with that (most likely: still proceed as
   anonymous, but the frontend could show a soft, non-blocking "your session expired,
   log in to see your own access level" hint instead of silently pretending the
   visitor never had an account).
2. Keep `get_optional_user_id` as-is (safe default), and instead have the frontend
   proactively drop a clearly-expired token from `localStorage`/the request before
   hitting a shared-plan endpoint, if it can cheaply tell the token is expired
   client-side (JWT expiry is readable without a network call). This avoids ever
   sending a stale token to these routes in the first place, sidestepping the
   ambiguity entirely — but doesn't help with a tampered-but-not-expired token.
3. Do nothing beyond documenting this — the current behavior (treat invalid token as
   anonymous) is arguably a reasonable default for a public-link feature, and the
   actual user-facing harm of the *current* bug (a stale-token owner/recipient
   silently getting anonymous-tier access instead of their real tier) may be small
   enough not to be worth new complexity. Worth deciding intentionally either way.

Whichever direction is chosen, the fix must **never** cause `get_optional_user_id` to
raise 401, given the documented reason the codebase avoids that on these routes.

## Files involved

- `backend/src/infrastructure/security/oauth2.py` (`get_optional_user_id`)
- `backend/src/infrastructure/security/jwt_service.py` (`decode_access_token`)
- `backend/src/modules/sharing/presentation/routes.py` (the only consumer)
- `frontend/src/api/client.ts` (the 401 interceptor whose behavior constrains the fix)
