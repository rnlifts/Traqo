# 2.5 — Repositories commit individually; no unit-of-work

**Status:** Confirmed valid, deferred. Not started.

## The finding

Every repository method that writes to the DB calls `self.session.commit()`
immediately, instead of the request (or use case) committing once at the end as a
single atomic unit. Confirmed count at time of writing: **29 `commit()` calls across
8 repository files** in `backend/src/modules/*/infrastructure/repositories/*.py`.

When a use case calls multiple repositories in sequence, there's no transactional
atomicity — if step 3 of a 4-step operation fails, steps 1-2 are already permanently
committed to the database. There is no automatic rollback of the whole operation.

## Proof this is a real, already-costly problem (not theoretical)

`backend/src/modules/sessions/application/use_cases/quick_start_workout.py` contains
hand-written compensating-delete logic specifically because of this:

```python
created_day = None
try:
    # Step 2: Create and persist the day
    ...
    created_day = self.day_repository.create(plan_day)
    # Step 3: Create and return the session
    ...
    return self.session_repository.create(session)
except Exception:
    # Something failed after the plan was created — clean up
    # everything created so far, in reverse order, so we don't
    # leave orphaned data behind.
    if created_day is not None:
        self.day_repository.delete(created_day.id)
    self.plan_repository.delete(created_plan.id)
    raise
```

This is a manual saga/compensating-transaction pattern, built by hand, to work around
the fact that a real DB transaction can't be used here — because each repository call
already committed before the next one even started. If this use case had proper
unit-of-work, this entire try/except block would be unnecessary: a failure would just
raise, the request-level rollback would undo everything, and the code would be
simpler and more obviously correct.

## The reviewer's proposed fix

```python
# database.py
def get_db():
    db = SessionLocal()
    try:
        yield db
        db.commit()
    except Exception:
        db.rollback()
        raise
    finally:
        db.close()
```

Plus: change every repository method from `self.session.commit()` to
`self.session.flush()` (writes to the DB within the still-open transaction, without
committing — auto-increment IDs are still available after flush, so callers reading
`created.id` right after a `create()` call keep working).

## Why this wasn't just applied

This is architecturally correct, but it's a request-lifecycle change that touches
**every repository in the app**, not a contained fix. Specific risks to think through
before doing this:

1. **Blast radius**: 8 files, 29 call sites, one central `get_db()` change. A mistake
   anywhere in that set could introduce a real data-integrity bug, which is exactly
   the kind of thing this change is trying to prevent — worth doing carefully, not as
   a drive-by.
2. **`quick_start_workout.py`'s compensating logic becomes redundant, not wrong** —
   once real unit-of-work exists, that manual cleanup code should be simplified/
   removed as a follow-up, not left in place as now-pointless defensive code.
3. **Test fakes**: the in-memory repository fakes used across `tests/unit/*.py` and
   `tests/conftest.py` don't model "flush vs. commit" at all (they just mutate an
   in-memory dict immediately). They'd keep passing either way, so they won't catch
   any transactional regressions from this change — real coverage would need to come
   from the integration tests (which use a real SQLite/Postgres session) or new tests
   specifically asserting rollback behavior (e.g., force a failure mid-use-case and
   assert nothing was persisted).
4. **Double-check no code relies on an early commit being durably visible** to a
   *different* DB connection/session mid-request (unlikely in this app's normal
   single-request-single-session flow, but worth a quick grep before assuming it's
   safe everywhere).

## Suggested approach when picking this up

1. Make the `get_db()` change first, behind nothing special — it's backward
   compatible on its own (a `flush()`-less repository still just commits early, which
   is today's behavior).
2. Convert repositories to `flush()` one module at a time, running the full test
   suite after each module, rather than all 8 files in one commit.
3. Add at least one new integration test per converted module that deliberately
   fails partway through a multi-step operation and asserts nothing was persisted —
   this is the actual behavior change being introduced, and today's tests don't cover
   it.
4. Once auth/sessions/workouts are converted, revisit `quick_start_workout.py`'s
   manual compensating-delete block and simplify it.
